> 최적화 문제 해결 기법
> - "이 상태에 도달하는 최선의 방법"에 중점
> - 배열/ 테이블로 이전 결과를 재활용한다.

> 접근 가능 문제
> - 최적 부분 구조
> - 중복 부분 문제 

### 메모이제이션?
1. 한 번 계산한 값을 저장해두고, 같은 계산이 다시 필요할 때 꺼내 쓰는 기법
2. 보통 재귀에 적용, 계산 결과를 배열, 딕셔너리에 저장

### 굳이?
- 중복되는 부분 문제를 반복 계산하는 것을 피하기 위해서
- 중복 계산을 줄이면 시간 복잡도를 줄일 수 있다.
- 재귀에서 주로 많이 생긴다. 재귀 자체가 작은 문제를 계속 호출하는 구조이기 때문에 같은 서브 문제를 여러 번 호출하게 된다.

### 구현!?
- 탑 다운 방식
- 함수 호출 전 해당 입력이 있는지 찾고 있으면 반환, 없으면 계산한다.

### 메모이제이션과 점화식?
- DP 구현 방식 중 하나
- 점화식(bottom-up)이 반복문 기반(점화식)이라면 메모이제이션(top-down)은 재귀 기반 탑다운

class `멀리 뛰기` {  
    //DFS  
    /**  
     * https://school.programmers.co.kr/learn/courses/30/lessons/12914?language=kotlin
     * */  
    @Test  
    fun solution1() {  
        val n = 4  
        val expected = 5L  
  
  
        assertEquals(expected, `top-down`(n))  
        assertEquals(expected, `bottom-up`(n))  
        assertEquals(expected, useStack(n))  
        assertEquals(expected, useRecursive(n))  
    }  
  
    @Test  
    fun solution2() {  
        val n = 3  
        val expected = 3L  
  
        assertEquals(expected, `top-down`(n))  
        assertEquals(expected, `bottom-up`(n))  
        assertEquals(expected, useStack(n))  
        assertEquals(expected, useRecursive(n))  
    }  
  
    private fun `bottom-up`(n: Int): Long {  
        return when (n) {  
            1 -> 1  
            2 -> 2  
            else -> `bottom-upUseRecursive`(1, 2, 2, n)  
        }  
    }  
  
    private fun `bottom-upUseRecursive`(first: Int, second: Int, count: Int, limit: Int): Long {  
        if (count == limit) return second.toLong()  
        return `bottom-upUseRecursive`(second % 1234567, (first + second) % 1234567, count + 1, limit)  
    }  
  
    private fun `top-down`(n: Int): Long {  
        return `top-downUseMemoization`(mutableMapOf<Long, Long>(), n.toLong())  
    }  
  
    private fun `top-downUseMemoization`(memoization: MutableMap<Long, Long>, number: Long): Long {  
        return when (number) {  
            1L -> 1L  
            2L -> 2L  
            else -> memoization[number] ?: run {  
                val result = `top-downUseMemoization`(memoization, number - 1)  % 1234567 +  
                             `top-downUseMemoization`(memoization, number - 2)  % 1234567  
  
                memoization[number] = result  
                result  
            }  
        }  
  
    }  
  
    private fun useStack(n: Int): Long {  
        var count = 0L  
        val stack = ArrayDeque<Long>()  
        stack.add(n.toLong())  
  
        while (stack.isNotEmpty()) {  
            val pop = stack.removeLast()  
            if (pop <= 1) {  
                count++  
                continue  
            }  
  
            stack.addLast(pop - 1)  
            stack.addLast(pop - 2)  
        }  
  
        return count % 1234567  
    }  
  
    private fun useRecursive(n: Int): Long = recursive(n)  
  
    private fun recursive(n: Int): Long {  
        if (n <= 1) return 1  
  
  
        var count = 0L;  
        for (i in 1..2) {  
            count += recursive(n - i)  
        }  
  
        return count % 1234567  
    }  
}

# DP: 경우의 수(Counting) vs 최단거리(Shortest Path)

## 핵심 결론

같은 격자 DP 구조(오른쪽/아래로만 이동)라도, "무엇을 구하는가"에 따라 **연산자**와 **초기값**이 완전히 달라진다.

|구분|경우의 수 DP|최단거리 DP|
|---|---|---|
|목적|(i,j)까지 가는 **경로의 개수**|(i,j)까지 가는 **최소 이동 횟수**|
|점화식|`dp[i][j] = dp[i-1][j] + dp[i][j-1]`|`dp[i][j] = min(dp[i-1][j], dp[i][j-1]) + 1`|
|연산자|합(+)|min|
|초기값 dp[0][0]|1|0|
|장애물(puddle) 처리|0으로 설정 (경로 없음)|무한대(INF)로 설정 (도달 불가)|

---

## 1. 왜 연산자가 다른가

### 경우의 수 DP → 합(+)

- (i,j)에 도달하는 경로는 두 갈래로 나뉜다: 위에서 내려온 경로들, 왼쪽에서 온 경로들.
- 이 두 갈래는 **서로 겹치지 않는 별개의 경로**다.
- 겹치지 않는 경우의 수를 합칠 때는 **합산**한다.
- 예: dp[i-1][j]=3, dp[i][j-1]=2 → (i,j)에 도달하는 실제 경로는 3+2=5가지.
- min을 쓰면 안 되는 이유: min(3,2)=2를 쓰면 나머지 3가지 경로가 존재하는데도 없는 것처럼 계산되어 틀린다.

### 최단거리 DP → min

- (i,j)에 도달하는 여러 경로 중 **가장 짧은 것 하나**만 필요하다.
- 나머지 경로는 버려도 정답(최단 거리)에는 영향이 없다.
- (i,j)는 (i-1,j) 또는 (i,j-1)에서 한 걸음 이동해서 도착한 칸이므로, 그 이동 1번을 항상 더한다.
- 예: dp[i-1][j]=3, dp[i][j-1]=5 → 위에서 오면 3+1=4, 왼쪽에서 오면 5+1=6 → 더 짧은 4를 선택.

### 왜 "최단"이라는 개념이 경우의 수 문제에는 없는가

- 오른쪽/아래로만 이동이 고정된 경우, (1,1)에서 (i,j)까지 가는 **모든 경로의 길이는 항상 동일**하다 (이동 횟수 = (i-1)+(j-1)로 고정).
- 따라서 "최단"이라는 개념 자체가 성립하지 않고, 남은 질문은 "그 같은 길이의 경로가 몇 가지 존재하는가"뿐이다 → 개수(합) 문제.

---

## 2. 왜 초기값이 다른가

### dp[0][0] = 1 (경우의 수)

- "경로가 1가지 존재한다"는 뜻.
- 출발점 자체에 도달하는 방법은 "이미 그 자리에 있는 것" 하나로 센다.
- dp[0][0]=0으로 두면 이 값이 전체에 곱/합 방식으로 전파되어 모든 칸이 0이 되어버린다.

### dp[0][0] = 0 (최단거리)

- "이동 횟수가 0번"이라는 뜻.
- 출발점은 이동 없이 이미 그 자리에 있으므로 0번.

**요약**: "개수를 센다" vs "거리를 잰다"의 차이가 초기값에 그대로 반영된다.

---

## 3. 장애물(puddle) 처리 차이

### 경우의 수 DP

- 장애물 칸의 dp 값을 **0**으로 설정.
- 이유: 그 칸을 지나는 경로는 0가지이므로.
- 갱신 시 장애물 칸은 갱신을 건너뛰고 0을 유지.

### 최단거리 DP

- 장애물 칸의 dp 값을 **무한대(INF, 예: Integer.MAX_VALUE)**로 설정.
- 이유: 그 칸에는 도달할 수 없으므로 "거리"가 무한대.
- 단, 실제 계산에서 INF 값이 그대로 다음 칸 계산에 더해지면 오버플로우가 발생할 수 있으므로, sentinel 값 비교 후 건너뛰는 조건 처리가 필요.

---

## 4. 1행/1열(경계) 처리 — 두 DP 공통 주의사항

일반 점화식 `dp[i][j] = dp[i-1][j] + dp[i][j-1]` (또는 min 버전)은 1행이나 1열에는 그대로 적용할 수 없다.

**이유**:

- 1행(i=0)에서는 `dp[i-1][j]`가 배열 범위 밖.
- 1열(j=0)에서는 `dp[i][j-1]`이 배열 범위 밖.

**처리 방법**:

- 경우의 수 DP: 1행은 `dp[0][j] = dp[0][j-1]`, 1열은 `dp[i][0] = dp[i-1][0]` (장애물이면 0).
- 최단거리 DP: 1행은 `dp[0][j] = dp[0][j-1] + 1`, 1열은 `dp[i][0] = dp[i-1][0] + 1` (장애물이면 도달 불가).

---

## 5. 한 줄 요약 (재구성용 원칙)

> **"겹치지 않는 여러 경로를 전부 세야 하면 합(+), 그중 하나만 골라도 되면 min이다."**
> 
> 그리고 min을 쓸 때는 "그 칸에 도착하기 위한 이동 1번"이 항상 함께 따라온다(`+1`).
